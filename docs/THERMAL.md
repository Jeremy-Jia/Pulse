# 小米 15 / 18 Pro 温控策略

Pulse 1.8 保留原有监测、悬浮窗、小部件和性能实验室，从首页「温控」进入。连接 Root 只验证权限和固件，点击「应用策略」才修改。不提供提权、BL 解锁或刷分区。

## 支持范围

| 设备 | 已匹配固件 | CPU 频率域 | 普通频率表上限 |
| --- | --- | --- | --- |
| Xiaomi 15 / dada | OS4.0.0.19.XOCCNXM.D01 | CPU0–5 / CPU6–7 | 3.5328 / 4.32 GHz |
| Xiaomi 18 Pro / hongkong | OS4.0.24.0.XFRCNXM | CPU0–2 / CPU3–5 / CPU6–7 | 3.744 / 4.032 / 4.704 GHz |

18 的 CPU6–7 还支持 4.8576 / 4.9536 / 5.0112 GHz 三个 Boost 档，均可选择。应用前另查 Boost 表与全局/策略 Boost 开关。普通表和 Boost 表分开校验；恢复时释放自身频率上限至驱动的 5.0112 GHz，不额外限制原厂 Boost。能够选择不等于能持续达到。

需要为 Pulse 单独授权 Root。检查温控程序、原厂密文、解码明文 SHA-256 和全部频率表，未知固件拒绝修改。频率域不单凭频率高低推断微架构。没有新增独立应用、广告或网络权限。

## 频率策略

- 全频：每个温度档使用该组所选上限。
- 阶梯增强：0–100%，25°C 档使用所选上限，其余档按增幅计算，向下取支持的频率。
- 逐档自定义：15 为 14 / 16 档，18 为 7 / 7 / 8 档；提供原厂、全频、当前增幅填充。

这是允许上限，不强锁频率、不添加超过普通驱动表的超频档。档位使用系统估算机身温度；原有触发温度、回落滞后、充电、Thermal HAL、内核与芯片保护保持。GPU 默认仍用原厂曲线，可在已适配的 18 上独立启用下面的 GPU 设置。调度、电流、功率与芯片温度仍可能限频。

## 小米 18 GPU 曲线（1.6）

在「策略」页启用「GPU 曲线放开」，选择 125–1450 MHz 的驱动原有频率档。默认关闭；15 不显示此选项，也不修改其 GPU。这里设置的是 35°C 起各温度档的允许目标，不强制低温空闲阶段限频。只改已验证普通配置 `[MONITOR-GPU]` 的六个 `target`，不改触发温度、回落滞后、BCL 电池电流保护或其他规则。GPU 电源档索引按实机频率表从快到慢映射，0 对应 1450 MHz；固件哈希和全部 26 档频率顺序必须匹配，否则拒绝启用。

GPU 与 CPU 共用当前会话、定时器和独立双守护。1.7 起，18 的机身温度进入下述持续调频环路；电池和可选 CPU 热点仍是独立停止条件。手动停止等退出操作会一起恢复原厂。调节在档位变化或检测到当前降频上限被重置时写用户频率上限，不锁固定频率，也不停止系统温控服务。控制台显示当前 GPU 频率与实际可用上限；设置上限不等于持续锁频。1.7 的上限读数合并 GPU 热限制与用户上限，避免只显示 `max_gpuclk` 而漏掉降频档；实际执行频率另列。配置加载与驱动执行存在异步延迟，以实际节点读数为准。18 的 CSV 在原字段后追加 GPU 当前频率、实际上限（Hz）、热限制档和开关状态；1.7 再追加 `cooling_level`、`cooling_percent`。15 的 CSV 格式不变。

Pulse 的 CPU 热点停止线只决定何时退出，并不改写厂商动态结温、SCMI 固件、电流或功率限制。设置 105°C 并不代表 CPU 在达到 105°C 前都不会降频。

## 温度与持续运行

机身温度来自 `/sys/class/thermal/thermal_message/board_sensor_temp`（系统估算值）。CPU 热点来自 `cpu-*` 热区的最高值；两者独立读取，52°C 只用于机身调节。

### 小米 18：机身温度调节（1.7）

默认 **估算机身低于 52°C 全释放，达到 52°C 才降频**。采用 CPU/GPU 性能优先策略；升级自动迁移原机身停止线为 52°C 调节上限，其他已保存的频率、GPU 开关、电池和 CPU 设置保留。设置页可选机身上限 35–52°C。配置修改在下次应用时生效。

- 正常档 100%；降频档依次为所选 CPU/GPU 上限的 80%、60%、40%、20%，取不超过目标的驱动档位；若低于硬件最低频率则取最低档。
- 达到降频线立即降一档，持续超线每约 5 秒再降一档；超过降频线 1/2/3°C 时至少进入第 2/3/4 档。
- 一旦低于机身上限，在下一次传感器采样时直接回到 100%，撤销额外 CPU/GPU 限频；不等待 49°C，不逐档延迟回升。恢复的是用户选定的性能策略，**不加载原厂曲线、不结束会话、不要求重新开启**。
- CPU 通过 CPUFreq 用户上限、已启用 GPU 通过 KGSL `max_pwrlevel` 用户上限调节。原本选定的加密曲线和会话 ID 全程保持。调节期间如用户频率节点被重置，下一次采样会重新施加当前降频档；低于温度上限时不循环强写最高频率。GPU 关闭时只调节 CPU；GPU 原有更严格用户上限不会被提高。
- GPU 上限写入前记录本会话可能写入的档位；手动停止、定时结束、独立守护接管后释放到原先的用户上限。检测到其他工具写入未知档位时不覆盖它。系统场景暂停期间释放额外调频上限，回到适配场景后再按实时温度调节。

电池停止线仍为 35–50°C（默认 45°C），可选 CPU 热点停止线为 70–110°C（默认关闭）。1.8 默认在独立温度触线时进入下述降温暂停；关闭自动恢复时仍退出。传感器/执行异常、守护异常、手动停止或计时结束均结束会话并取消自动恢复。52°C 是软件调节起点，采样周期与热惯性可能带来超调；不代表能把温度硬性固定在 52°C。

### 小米 18：独立保护后自动恢复（1.8）

设置页「降温后自动恢复」默认开启，电池默认恢复温度 42°C，CPU 热点默认恢复温度 75°C；分别可设 30°C/60°C 起至对应触发温度以下 1°C。机身调节上限仍为 52°C，三种温度分别读取、分别判断。关闭 CPU 热点保护时，不把 CPU 恢复温度列为等待条件。

1. CPU 或电池达到独立保护线，暂时加载已验证的原厂普通曲线、释放 Pulse 用户频率限制，进入 `thermal_paused`。保留同一会话、原 CPU/GPU 设置、Root 主守护与第二守护。
2. Root 守护唤起 Pulse 自己的前台服务，服务通过 Android `NotificationManager` 的「温度保护与自动恢复」通知渠道发布原因、当前温度和等待条件。前台常驻通知继续显示降温等待，并提供「停止自动恢复」。
3. 所有恢复条件同时满足、适配的普通场景返回，稳定至少 5 秒后重新校验固件与覆盖归属，加载本会话原先的曲线，恢复所选 CPU/GPU 上限并发出恢复通知。不创建另一个会话，不恢复其他工具写入的未知配置。
4. 手动停止会立即标记取消恢复；定时模式在等待降温期间仍计时，到期即结束。守护丢失、传感器/配置/服务异常也会退出，不因温度下降自动重启。重启后临时 Root 消失，仍保持原有的本次开机限制。

系统通知权限已在实机确认开启。通知是否发声取决于系统通知渠道与勿扰设置。控制和恢复由 Root 守护执行，通知由 Android 前台服务发布；无需保持设置界面打开。

### 小米 15

保留原来的电池、估算机身 35–50°C 停止线与可选 CPU 热点 70–110°C 停止线。默认电池 45°C、机身 43°C、额外 CPU 线关闭。触线恢复并停止，之后需手动重新启用。

定时模式为 1–1440 分钟；持续模式无倒计时。退出界面、后台冻结或返回前台本身不停止 Root 守护。15 保留「重启后继续」：开机先恢复再校验重启；手动或触线停止的会话不会再次启动。运行中切换「重启后继续」会立即把 `resume_boot` 写入当前会话的 `policy.env`，并确保 `/data/adb/service.d/70-pulse-thermal.sh` 存在；切回定时模式会同时关闭该启动钩子。已在 15 / OS4.0.0.22 上完成真实重启验证：启动钩子执行并返回 `OK ACTIVE`，同一会话恢复运行。OTA 会覆盖 KernelSU，需要重新修补 `init_boot`。若启动钩子未被 Root 管理器执行，应用侧无法替代；仍可检查 `/data/adb/pulse-thermal/boot.log` 与 `/data/adb/service.d/70-pulse-thermal.sh`。

18 当前使用临时 Root，禁用开机继续。全局挂载命名空间中的临时绑定目录覆盖配置路径，原厂物理目录保持为空；重启后挂载消失，不依赖重启后仍有 Root 执行恢复。

持续模式遇到其他系统场景配置时暂停，保留温度守护和手动恢复；仅在已验证普通配置返回后继续，不向游戏或充电配置强行写入普通曲线。定时模式遇到未知配置仍停止恢复。场景数值变化但配置未变，不再无条件停止。

## 状态与恢复

1.9.1 返回前台主动重新读取 Root 状态；核对期间和读取失败时显示“正在核对状态”，既不声称运行也不声称原厂。状态检查守护 PID、进程启动时间、命令行与 30 秒内的单调时钟心跳，识别 PID 复用和进程挂起。磁盘 phase 仍为 active、实际守护失效时返回 `unprotected`；应用轮询会恢复原厂并确认结果。恢复失败保持异常状态和重试入口。

双守护经 `setsid` 启动并移出 Android 应用 UID cgroup，降低随应用强制停止、冻结或内存回收一起退出的概率；相互核验心跳，任一失效由另一个恢复。二者均被杀时，打开 Pulse 触发核对与恢复，不会把残留覆盖配置显示为正常运行。重新打开已运行的会话会接回前台状态通知。单次强制停止测试不等于对所有系统后台策略的永久保证。

控制程序升级先由旧版本恢复；正在运行的不限时会话复制实际原策略到新会话，再校验启动。不会读取未应用的 UI 草稿作为恢复设置；计时或等待降温的会话在升级时安全结束，不延长计时或绕过降温条件。Root 进度与错误在全部温控子页显示。

前台通知显示温度、计时和恢复操作。Root 主守护及独立第二守护不依赖界面；Android 冻结可能延迟通知刷新。CSV 包含各组频率、上限、温度、电流、电压、场景和状态。电池净功率不等于 SoC 功率。

运行资料位于 `/data/adb/pulse-thermal`。APK 与源码不包含厂商程序、完整配置、密钥或设备备份。15 从匹配程序读取编码材料；18 加载其用户态私有副本，禁用副本构造函数，仅调用固定且经过验证的初始化函数，临时文件用后删除。两种适配均要求原厂往返逐字节一致。

普通配置只修改 CPU `target` 行，以及 18 上用户启用的 GPU `target` 行，加载后核对实际明文哈希，失败恢复。1.7 的机身调节另使用 CPUFreq/KGSL 用户上限，不改写原厂曲线或硬件保护阈值。15 使用启动恢复脚本；18 使用重启即消失的挂载。恢复只移除 Pulse 自己的覆盖和挂载。卸载前请先恢复原厂。

在 Android Root shell 中恢复当前会话：

```sh
id=$(cat /data/adb/pulse-thermal/current)
/system/bin/sh /data/adb/pulse-thermal/runner.sh restore "$id" MANUAL
```

## 验证

`tools/ThermalCodecTest.java` 回归 15 历史配置逐字节一致；`Thermal18CodecTest.java` 验证三组曲线、各增幅、自定义及其他保护不变。另外验证 18 全部 26 个 GPU 档、非法频率拒绝和 GPU 关闭时的旧版字节一致性。本地固件和临时编码材料不入库。

18 的硬件测试：`adb shell am instrument -w -e thermal true -e thermal_scope mi18 dev.pulse.monitor.test/dev.pulse.monitor.MonitorInstrumentation`。会应用有停止线的策略，先恢复已有会话，并保持 Pulse 前台，避免 HyperOS 暂停测试线程。检查真实 Root、全局挂载、状态同步、一分钟计时、守护异常恢复、原厂哈希和空覆盖目录。真实重启不以模拟检查代替。

详见 [1.5 记录](verification/thermal-1.5.0/REPORT.md)；15 此前硬件证据见 [1.4 记录](verification/thermal-1.4.0/REPORT.md)。

1.7 控制器回归：`python3 tools/test_body_control.py --adb /path/to/adb --serial SERIAL`，直接执行随 APK 发布的 shell 函数，在临时文件中测试精确 52°C 边界与低于上限立即全释放、旧会话滞后规则兼容、CPU/GPU 上限、场景暂停、崩溃写入恢复、外部上限及独立停止保护，不写真实 sysfs。真实低温阈值调节证据见 [1.7 验证记录](verification/thermal-1.7.0/REPORT.md)。

1.8 同时回归 CPU 75°C、电池 42°C、机身 52°C 的独立恢复条件、暂停/恢复状态、通知事件和手动取消。实机使用较低的 CPU 70/65°C 测试线触发保护，验证通知与同会话恢复，不故意加热到 CPU 105°C 或机身 52°C。见 [1.8 记录](verification/thermal-1.8.0/REPORT.md)。
