# Pulse 1.8.0：独立保护通知与自动恢复

2026-10-22，hongkong / OS4.0.24.0.XFRCNXM，Android 17，临时 KernelSU。版本 1.8.0 / versionCode 10，覆盖安装保留应用数据。

## 最终设置

- 估算机身低于 52°C 全释放，到 52°C 仅调低 CPU 与已启用 GPU 上限；这是机身温度，不是 CPU 温度。
- 独立保护触发：CPU 热点 105°C、电池 50°C。触发后暂用系统原厂曲线降温，会话和原性能设置保留，系统通知解释原因。
- 自动恢复开启：CPU 热点 ≤75°C、电池 ≤42°C、估算机身 <52°C，同时稳定至少 5 秒后恢复本会话原 CPU/GPU 曲线，并发恢复通知。
- CPU 组上限 3.744 / 4.032 / 5.0112 GHz，GPU 曲线目标 1450 MHz，持续运行。实际频率仍受负载及底层保护影响。
- 手动停止、计时结束、守护异常、未知配置或固件变化不自动重启。15 保持原来的控制行为，本次未连接 15 做实机测试。

## 验证结果

`assembleDebug assembleDebugAndroidTest` 离线编译成功。生产 shell 函数在主机 dash 和手机 `/system/bin/sh` 中通过边界测试：52°C 性能调节，75/42°C 恢复条件，三个传感器条件分别阻止提前恢复，暂停/恢复状态与通知事件，外部场景归属，手动取消。

实机为了验证路径，临时使用 CPU 70°C 触发、65°C 恢复的较低测试线，电池恢复 42°C、机身上限 52°C；每个 CoreMark 工作进程独立限时 12 秒。本测试不是计分测试，也未故意加热到 CPU 105°C 或机身 52°C。

1. 实际温度触发 `CPU_LIMIT`，转为 `thermal_paused`，核对原厂明文曲线；系统 `cmd notification get` 确认 Pulse 的渠道 `pulse_thermal_alerts`、通知 ID 72 已发布暂停原因和等待条件。
2. 工作负载结束，恢复条件稳定后自动回到 `active`，会话 ID 保持一致、原先解锁曲线哈希一致；系统通知显示“降温完成 · 已恢复性能策略”。
3. 等待降温时手动停止，温度回落后仍保持停止。
4. 等待降温时真实计时到期，结束会话、撤销频率限制、移除临时挂载。
5. 等待降温时 SIGKILL 主守护，独立第二守护以 `WATCHDOG_LOST` 结束并恢复，未重新启动性能策略。

结果见 `hardware-report.json`、事件文件及两份系统通知摘录。之后在应用界面保存并启用正式的 105/75°C、50/42°C、机身 52°C 配置，读取 Root 状态核实自动恢复开关和全部阈值，设置页截图确认 75/42°C 显示。
